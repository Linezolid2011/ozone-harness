# M4 Dream memory 设计说明（**已退役**）

> ⚠️ **这份文档描述的那套东西已经不在了**。保留它是为了记住"当初为什么那样做、
> 以及为什么后来判定它错"。
>
> M4 的 dream 是**对 `memories` 表做外科手术**：合并、改写、提炼洞察、清理、补别名。
> 它的问题不是做得不好，而是**作用对象错了** —— 用户在对话里明确要求记住的事，
> 会被这个后台整理者改写、合并甚至删掉。那不是缺功能，是**越界**。
>
> 现在 dream 只写**背景档案**（`data/vault/`），碰不到记忆条目：
> 见 [M7 Dream vault 设计说明](10-dream-vault.md)、ADR-053（两套系统分家）、
> ADR-059（那套工具连同它的运行表一起退役）。
>
> 留下来的**形状**是它的安全设计：独立的 agent、独立的预算、
> 快照 / 预演 / 审查 / 回滚 —— 这些现在都用在了档案上。

## 一句话

dream 不是"总结聊天记录"，而是**对记忆库本身做一次离线外科手术**：
合并重复、解决冲突、提炼洞察、清理噪声。

> **两处更新**：① 「补检索别名」已随 M2 检索机制一起删除（ADR-058）——
> 别名本来只为「某条记忆会不会被检索到」服务，检索没了它就没有读取方；
> ② 方向已定：dream 以后只写背景档案、不再改写记忆条目（ADR-053），
> 所以下面这套「对记忆库做手术」的工具会在整理流水线落地后整体下线。

## 为什么要做成第二个 agent

对话模型的第一职责是**如实记录**。整理需要判断力（该合并还是该保留？这条还有价值吗？），
而且带破坏性。把两者混进一个工具集，等于让记录者随时有权限重写历史。

所以 dream 用**自己的工具集**，而**共用同一个 AgentLoop**：

| | 对话 agent | dream agent |
|---|---|---|
| 工具 | `mem_create` `mem_edit` `mem_del` | `mem_merge` `mem_rewrite` `mem_alias` `mem_forget` `mem_insight` |
| 提示词 | 身份 + 记忆 + 当前问题 | 整理目标 + 记忆清单 + 近似重复候选 |
| 预算 | 聊天预算 | **独立的** dream 预算 |
| 触发 | 用户每说一句 | **只在显式 `--dream` 时** |

共用循环的做法是在 `AgentLoop` 里注入一个 `Planner`：
对话的 planner 每轮规划一次记忆注入（ADR-009），dream 的 planner 就是
"固定 system + 累积的工具消息"。**熔断、流式拼装、工具执行、事件日志因此只有一份实现** ——
熔断尤其不能有两份，那是"钱"的防线。

## 五个整理动作

| 工具 | 作用 | 关键约束 |
|---|---|---|
| `mem_merge(ids, content)` | 多条 → 一条 | ≥2 个有效 id；结果是新条目，原条目软删除；来源取并集 |
| `mem_rewrite(id, content)` | 改写措辞让它更自包含 | 不改事实含义 |
| `mem_forget(id, reason)` | 删除失去价值的记忆 | 必须给 reason，写进审计日志 |
| `mem_insight(content, source_ids)` | 提炼更高层结论 | **`source_ids` 必须全部真实存在** |

## 增量与预算

`dreamed_at` 游标：候选按「从没整理过 → 最久没整理过」排序，每次只取 N 条（默认 80）。
**是降优先级，不是只处理一次** —— 否则质量下降的记忆永远没有第二次机会。

dream 有自己的一整套预算，与聊天互不侵占：

```
HARNESS_DREAM_MAX_MEMORIES=80       单次最多整理多少条
HARNESS_DREAM_MAX_STEPS=12          最多几步工具调用
HARNESS_DREAM_TOKEN_BUDGET=40000    单轮累计 token 上限
HARNESS_DREAM_MAX_OUTPUT_TOKENS=4096 单次输出上限（必须够大，见"踩过的坑"）
HARNESS_DREAM_WALL_SECONDS=300
HARNESS_DREAM_MAX_INSIGHTS=5        每轮最多几条洞察
```

## 安全设计

```
--dream --dry-run     真跑一遍 → 算出 diff → 整体回滚 → 只报告"本来会改什么"
                      并且**不推进游标**，下次还会挑中同样的条目
--dream               真正应用改动，运行前整体快照进 dream_runs.snapshot
--dreams              列出历史运行（含改动数）
--dream-review RUN    逐条 before/after diff + 模型总结 + 完整轨迹路径
--dream-undo RUN      用快照整体还原；运行状态标记为 undone
```

回滚**只还原 `memories` 表，故意不还原 `memory_ops`**：审计日志应当保留
"发生过什么"，包括 dream 与回滚本身。所以回滚后 ops 计数还会 +1。

**禁止编造的机械保障**：`mem_insight` 要求 `source_ids` 全部是真实存在的记忆。
模型至少无法凭空发明一条没有依据的洞察。
但机械保障**不能保证依据真的支持结论**，所以 `--dream-review` 的人工审查仍不能省。

## 实测记录

演示库 167 条记忆（45 条真实语义 + 122 条刻意填充的噪声）。

**只整理前 40 条（都是有效记忆）**：

| | 预演 | 真实运行 |
|---|---|---|
| 步数 | 2 | 3 |
| token | 9,834 | 17,511 |
| 改动 | 18 处 | 29 处 |

做对了：4 条咖啡偏好合并为 1 条且**信息无损**（美式/拿铁/手冲/不加糖全在）；
2 条洞察的 `source_ids` 真实有效；给「会弹吉他」补上 `乐器/弹琴/音乐`——
这正是 M2 语义鸿沟的修复。

**整理 80 条（含填充噪声）**：39 条碎片记忆被合并成 5 条（咖啡偏好、技术文章、
用过的工具、负责过的模块、出差城市），另 1 条洞察，16,651 token。

观察到的两点：

1. **它一次都没用 `mem_forget`**，即使面对明显的填充噪声也选择合并。
   这与"删除是最后手段"的要求一致，是期望中的保守行为 ——
   但意味着"清理"以合并形式发生：条数下降，信息不丢。
2. 它把「电脑是 Windows」与「手机是安卓」合并了。**过度合并会降低可编辑性**
   （换手机就得改写整条）。据此收紧了提示词，加了可操作判据：
   "合并后如果其中一部分变了、另一部分不会跟着变，那它们就是两个独立事实"。

## 踩过的坑（值得单独记住）

**1. 输出预算必须由循环显式传递给 provider。**
`max_tokens` 原本是 provider 从自己构造时的 Settings 取。于是 dream 改自己的 settings
**完全无效**，provider 仍按聊天配置发 2048 —— 整理 80 条记忆时 reasoning 用满 2048、
零工具调用。修正：循环显式传 `max_tokens`。原则是"谁定预算谁负责传递"。
（这个无效修复是被一条断言 `provider.calls[0]["max_tokens"] == 1234` 抓出来的。）

**2. `finish_reason == "length"` 必须显式暴露。**
上一条的后果暴露了第二个 bug：被截断的回复被当成 `stop_reason=completed`，
**"模型想到一半被砍断"伪装成了"本轮无事可做"**（改动 0 处，看起来一切正常）。
这个静默失败比崩溃危险得多。

## 已知局限

- ❌ 没有对话历史回放：dream 只看记忆条目，不看它们是从哪段对话来的。
  语义模糊的记忆（例如「用户不喜欢开会」到底指哪种会议）无法从历史中补全上下文。
- ❌ 语义鸿沟只被"别名"部分覆盖：dream 想不到的说法仍然召不回。
- ❌ 没有跨记忆的一致性校验（例如"住在上海"与"通勤靠 10 号线"是否地理自洽）。
- ❌ 洞察的正确性没有自动校验，依赖人工 `--dream-review`。
